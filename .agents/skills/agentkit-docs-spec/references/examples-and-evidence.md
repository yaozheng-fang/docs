# 示例与事实依据

来源：Google ADK 的 integration-create、integration-review、adk-bot-review、api-reference-audit，以及 Google 的 Code samples、Procedures。标识 E 用于来源覆盖清单

## E1 事实来源

- 先确定目标产品、SDK、版本和文档性质，随后核对该版本的公开 API、实际命令帮助、公开配置或协议
- 不默认任何贡献者或工具提供的示例正确，也不以 PR 描述、旧文档或发布标题替代源码及公开行为核验
- 对每个例子核对用到的类、方法、参数、返回结构、异步行为、依赖和注册方式；第三方 SDK 同样核对
- 本地没有源码时，可以通过公开仓库或官方文档取得依据，不假设固定本地 checkout 存在
- 发布文档以目标发布版本为准，不能拿超前的 main 证明稳定版本支持某能力；确实属于 Preview 的功能明确标注
- 检查相关已关闭、已拒绝和已合并的修改，避免重复记录、重新引入已弃用方案或覆盖已有修正
- 内部核验可读实现，但公开正文只说明用户需要的行为、接口和限制，不贴内部调用链作为论证

## E2 参数、依赖与版本

- 参数表覆盖名称、类型、默认值、用途以及实际相关的必填性、范围和条件；默认值和优先级不能靠名称推测
- 确认 PyPI/npm 等包真实存在，指定版本已发布，语言版本要求与文字一致；不能给用户一个不存在的安装命令
- 使用真实的规范导入方式、入口变量和导出形式，并在同一组例子中保持一致；具体名称遵循目标 SDK，不复制其他产品的固定写法
- 模型标识必须在目标环境可用。稳定别名可以减少维护成本，但不能凭空构造别名，也不能把产品模型替换为 Google 示例模型
- 区分“当前文档对应版本”“功能首次引入版本”“最低兼容版本”和“为复现而固定的版本”，不能一律改成最新版
- 版本审查需读取实际版本标记、发布记录和包仓库。单仓库发布多包时确认比较的是正确包；索引可能滞后，冲突时说明两个来源及采用依据
- 同一 SDK 的 API、CLI、REST 等参考面若应跟随同一版本，检查它们是否一致；没有显式版本标记时按实际公开 schema 或类型集合核对，不能靠子串命中判断覆盖
- 引用的路径、脚本和版本标记是待核实线索，不能把静态映射当永久事实；项目结构或更新流程变化时重新定位
- 由上游生成的参考页面若会被重新生成覆盖，应修改对应源说明或使用项目既有生成流程，不能只修生成产物而隐瞒维护问题

## E3 完整且最小的示例

一个号称可运行的例子必须提供必要的导入、依赖、配置、初始化、调用入口和上下文，或者清楚引用同页已经建立的上下文。它应完成一个明确任务，并说明如何判断结果

- 在例子前说明它演示什么，必要的账号、资源、网络、凭证和版本先准备
- 命令标明执行目录；分清 shell 环境变量、`.env` 文件和配置文件，不能把不会导出的 shell 赋值当成已传入子进程的环境变量
- 解释需替换的占位符及其来源，不默认服务器地址、项目、用户、会话或资源已存在
- 用有意义的虚构名称，不用无意义的 foo/bar，也不写真实密钥、内部地址或真实个人资料
- 可选安装和配置写清包含什么、引入什么行为；提到扩展点就给实际使用方式
- 多种方式先给推荐路径，替代方式说明差异；Python、TypeScript 等不同语言的例子分别验证，不仅翻译文字
- 声明支持本地与远端连接时，两种示例都完整；声明支持某个语言时有相应证据
- 输出示例紧随相关命令，说明变化字段、结果含义或可检查状态；不要让读者从一长段日志自行猜测成功
- 涉及资源创建、远端访问、敏感内容或费用时，在相关动作前说明实际影响

## E4 代码展示

- 使用带语言标签的围栏代码块，按目标语言和项目惯例缩进；Python 等语言不能为了统一外观改成不符合惯例的缩进
- 区分可运行代码、完整配置、配置片段、命令输出、公开签名和伪代码。长命令换行必须保留正确续行语法
- Google 的 80 字符建议用来改善代码与英文源码的阅读，不作为破坏长 URL、字符串、表格、中文语义或既有格式的理由
- 省略内容优先用该语言的注释明确说明，不用裸省略号伪装成完整代码；Python 的公开签名中允许合法的 `...`，但必须说明那是签名而不是实现
- 有省略内容的块不能宣传为复制即可运行；提供完整版本或清楚写明补全方法。站点支持时避免对不可执行片段呈现误导性的“一键运行”体验
- 代码前的引言应说明作用，避免统一写“运行以下命令”；代码之后解释必要结果，不逐行复述显而易见的语法
- 只在修正功能、错误、可理解性或明确格式要求时改示例，不为文风顺手重命名变量、重新格式化或改语法

## E5 链接与资源

- 链接来源真实，目标与文字承诺一致；怀疑虚构的仓库、示例或文档链接时实际检查，不猜一个相似 URL 顶替
- 内部链接按站点根路径规则书写，确保预览环境可访问。只改域名或扩展名不等于已经验证目标
- 外链通常应正常返回并展示预期内容；权限、限流或网络失败应标为尚未验证，不能直接认定链接不存在
- 图片和图标文件实际存在且能解码，路径相对关系正确；卡片图标尺寸、比例和展示要求遵循目标站点
- 使用同类页面或仓库实际目录核对资源路径，不凭猜测添加 `../` 或部署前缀
- 页面改名或迁移时检查导航、引用和重定向；必要重定向直接指向最终页面，不形成重定向链
- 相关资源优先指向稳定的官方产品文档、源代码、包仓库和凭证获取页；对厂商深入能力使用链接，避免重复维护其完整手册

## E6 验证与交付范围

核验分三类，报告时分开说明：

| 检查 | 可以得出的结论 | 不能替代的内容 |
| --- | --- | --- |
| 写作与结构检查 | 读者信息、页面组织和语言是否清楚 | API 真实存在、示例能运行 |
| 来源核对 | 名称、参数、版本和行为有依据 | 凭证、网络及部署环境中的实际成功 |
| 执行与渲染验证 | 已验证环境中的示例和展示可用 | 所有平台、版本或全部外部环境可用 |

深度审查在条件允许时运行完整示例或最小等价验证，并检查页面渲染、图标和链接。用户只要求粗看时，不扩张为云上测试或批量联网检查；先报告可直接确认的问题和待验证项

发现产品自身问题与厂商 SDK 问题时分清归属。修复只覆盖用户要求的范围，不私自修改第三方仓库。无法验证的内容标明限制，不把“没验证”写成“有错误”或“已通过”
