# 写作与表达

来源：Google ADK 的 integration-create、integration-review、adk-bot-review，以及 Google 写作指南的 Highlights、Voice and tone、Headings and titles、Procedures、Notices。标识 W 用于来源覆盖清单

## W1 读者、目的与语气

- 以读者要理解的概念或完成的任务为中心，先给有用的信息，不先介绍实现细节或复述作者的工作过程
- 给足首次理解所需背景，同时尊重读者时间；明确的主题不需要空泛开场和重复小结
- 英文清晰、自然、友好而克制，不写俚语、网络缩写、流行梗、文化笑话、夸张感叹或居高临下的措辞
- AgentKit 中文采用正式书面语；“正式”不等于使用官样文章、长定语或晦涩词语
- 不写无法验证的营销承诺，例如“强大的一站式方案”“轻松保障安全”；说明具体能力、适用条件与边界
- 不用“只需”“显然”“很简单”“simply”“it's easy”“quickly”等评价操作难度或暗示速度；有可核实的时延或步骤数时直接给事实
- 不提前宣布尚未公开的产品能力。明确属于目标 Preview 的内容按仓库规则标注，不能混入稳定版本
- 删除“请注意”“在目前这个时间点”等无信息前缀，不反复用“你可以”“To do”开头，也不把每条指令都写成“please”
- 保持尊重和包容，不贬低群体，不假设读者来自某个文化、地区或拥有某种身体能力
- 读起来拗口时，重新确认要传达的事实，优先拆解复杂句；可以朗读检查，不为了活泼而添加玩笑或比喻

## W2 句子与指代

- 用主动语态，说明执行动作的是用户、CLI、平台还是智能体；英文通常用一般现在时描述现有行为
- 面向操作者时用第二人称或直接指令；英文优先用 you，而不是 we。确实指读者所开发软件的终端用户时，再用 user
- 条件、执行位置和必要目标放在动作前；动作产生的结果和解释放在动作后
- 英文避免孤立使用 this，写 this command、this configuration 等；中文“它”“此处”“该能力”必须有明确指向
- 用简单、具体的动词，英文通常用 use、start 等，不用 leverage、utilize、commence 堆砌专业感；专门技术含义除外
- 不堆叠定语、名词串和双重否定，确保 only 等限定词修饰对象明确
- 一个段落围绕一个意思，第一句提供最重要的信息；句子简短但连贯，不拆成生硬碎句
- 同类列表保持相同句法、时态、大小写和标点；必要时重复主语、条件词或名词以消除歧义

| 原表达 | 建议表达 | 原因 |
| --- | --- | --- |
| 只需简单配置，即可轻松接入 | 配置服务地址和 API Key 后，将工具注册到智能体 | 说明动作及前提 |
| 配置会被自动读取 | CLI 在部署时读取项目目录中的配置文件 | 明确执行者和时机 |
| This is required before deployment | This credential is required before deployment | 指代明确 |
| 运行以下命令 | 创建项目 | 用动作目标介绍命令 |
| `RedisConfig` defines the connection | The `RedisConfig` configuration defines the connection | 用名词解释标识符 |

## W3 标题

- 文档标题由主要目的决定：教程和操作指南用任务型标题，概念页用名词短语，同一页可按各节目的混合使用
- 英文任务型标题用动词原形，例如 Create a session；概念标题用 Session lifecycle。尽量不以 -ing 动词开头，Billing、Pricing 等没有更好替代的惯用名称可保留
- 英文采用 sentence case，产品名和公开标识符保留正确大小写
- 标题具体、可区分，避免重复页面标题、笼统的“API”“使用方法”或过长的“示例：如何……”
- 不用数字表示章节顺序；版本号等内容标识可以保留。需要编号的是操作步骤，不是标题
- 可选章节在开头说明“可选：”或“Optional:”，并说明适用条件
- 缩写只在足够常见时用于标题；必要解释放到随后正文，中文不要用冗余括号译名代替说明
- 标题中减少标点，不放链接，不把长命令和代码表达式当作操作指南标题
- CLI/API 参考允许保留命令、路径和接口名；必要时加描述性名词，以目标仓库规范为准
- 一页只有一个主标题，按 H1、H2、H3 组织，不跳级，不为字号调整标题级别；Mintlify 已显示页面标题时不要再重复 H1
- 父标题后必须有实质内容，不能连续堆叠空标题；可合并层级，也可补充有用的分组解释，不能填空话
- 介绍一组子章节时，明确说“以下各节”或 the following sections，避免用 this section 模糊指代多个章节

## W4 段落、列表与表格

- 长段落拆成有逻辑的段落、章节或列表，保留句间必要联系，不添加机械过渡语
- 有执行顺序的内容用编号步骤，无顺序的并列内容用项目符号；相关名词和释义用说明列表或简单表格
- “术语：解释”用冒号，不用破折号拼接；正文中的长破折号优先改成独立句或自然连接
- 减少只有一段代码的零碎小节。端到端示例通常比把 Setup、Observe 等机械拆开更清楚
- 表格用于比较或查询，不用来排版正文；先说明表格用途，表头明确，尽量不合并单元格
- 技术标识符使用代码格式，UI 控件名称使用加粗；普通产品名、正文和全部段落不应滥用代码字体或强调
- 英文不要用 ALL CAPS 强调，也不要以 & 代替正文的 and；真实 UI 名称、代码和空间有限的标签除外
- 英文采用美式拼写、标点和 serial comma；同一文档保持一致，不机械套用到中文
- 日期和时间无歧义，例如 2026-09-19；跨地区操作写清时区，单位和币种明确

## W5 步骤

- 过程说明先交代额外背景，不重复标题；背景已经充分时不必再加引言
- 引言和每一步应是完整表达，不让列表条目补完一个悬空的半句话
- 每一步完成一个明确动作，首句尽早出现动作动词。连续的短菜单操作可以合并，复杂动作应拆开
- 一步流程直接写动作，不人为建立“第一步”的框架；多层步骤尽量浅，使用站点组件或渲染器支持的编号，不硬编码不受支持的层级
- 常用顺序：动作说明、命令或配置、占位符解释、必要解释、预期输出、结果含义。相关危险提示应前置
- 说明在哪个控制台、项目目录、文件或工具中操作；分成多个可独立阅读的过程时，分别交代位置
- 可选步骤以“可选：”开头，不把必需步骤写得像可选；目标表达如有歧义，直接说明该动作是必需的
- 动作后给结果，避免下一步再次完整重复上一结果；必要理由也放在动作后
- 需要按 Enter 才生效时写在该步中。使用控件标签而不是“右边”“铃铛图标”等视觉描述
- 不用常规复制粘贴快捷键增加噪音；任务确实依赖快捷键或无障碍操作时说明对应平台
- 同一任务优先给最短、可访问且读者熟悉的推荐路径；确需多个平台或方式时，用分节或标签页说明适用差异
- 引用已经说明的重复过程，不复制整段；减少步骤中的长篇岔路和无关背景，一次让读者处理一个决定

## W6 提示、警告与成功结果

- 提示框用于正文之外的有用补充，避免连续或嵌套多个提示框；无法判断时先写成正常正文
- 必要步骤、前置条件、正常结果和普通交叉引用应在读者必经路径中，不依赖读者打开或留意一个旁注
- Google 的 Note 表示可跳过的补充，Caution 表示需谨慎，Warning 表示显著风险或不可逆影响
- AgentKit 使用 Mintlify 对应组件。若产品规范明确要求用 `<Note>` 列前提，应在操作前醒目放置，并在相关步骤中明确依赖，不能当可选提示隐藏
- 警告说明具体动作、影响范围和可用的避免或恢复方式，不为没有依据的假设风险增加通用警告
- 静态文档用文字描述预期成功结果，不写成已经替读者完成了操作；Google 的 Success 提示仅适合实时交互状态
- 引言紧接代码或步骤时可以用冒号；中间插入不相关说明后，不让冒号错误地指向后面的块

## W7 编辑范围

- 新写前参考同类已发布页面，语气、标题、术语与结构保持一致，同时遵循更高优先级规范
- 更新优先做满足需求的最小修改；除非页面整体难以理解，不进行无关重写或全面翻新
- 不无故删除已有内容，不仅为个人风格改变示例变量、空格或语法；修正会影响使用的内容应有依据
- 对未核实事实保留清晰的核实状态，不把不确定的功能、默认值或效果润色成肯定结论
