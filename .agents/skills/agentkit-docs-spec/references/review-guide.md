# 审查方法

来源：Google ADK 的 integration-review、adk-bot-review、api-reference-audit 和 CONTRIBUTING。标识 R 用于来源覆盖清单；仓库运营事项仅在相应 PR 审查中适用

## R1 审查深度与范围

| 用户要求 | 处理方式 |
| --- | --- |
| 大致看看、先看质量 | 阅读代表页面和上下文，给少量已确认问题，不改文档，不跑全面测试 |
| 完整检查某些页面 | 按写作、结构、示例、链接、双语等适用维度逐项检查，记录覆盖范围 |
| 审查文档 PR | 阅读完整累计差异、相关正文与必要来源，给具体发现及审阅建议 |
| 修复发现的问题 | 只修改用户授权范围，保留作者无关内容，按实际改动验证 |
| 评估第三方集成是否应收录 | 在技术与写作审查之外，开展 R7 的价值与成熟度核实 |

关键词扫描只能产生候选项。例如版本标题中的数字不是步骤编号；参数表里的破折号不是正文滥用标点；英文页中的中文测试样本未必是漏译；合法签名中的省略号也不代表示例损坏

完整审查需说明已检查的文件、版本和维度；粗看不能被描述成“全站已审计”。不要为了输出问题数量，把合理取舍或未验证事项当成缺陷

## R2 获取变更与核对意图

- PR 审查读取完整累计 diff，而不是单个提交；导航、资源或遗留配置可能出现在较早提交中
- 本地审查查看工作区状态与差异，保留用户未提交内容，确认审查的是用户要求的基线
- 确认标题说明实际变更主题；追溯关联 Issue 中的具体需求，不只看编号
- 多个 PR 涉及同一项需求时一起核对覆盖和重复；涉及不同需求时分开评估，确实无法确定范围才澄清
- 搜索相关关闭 Issue、已合并或已拒绝的 PR，确认没有重复、已经被替代的内容或维护者明确否决的方案
- 检查变更放在正确页面、是否提供有用的学习或操作路径、篇幅是否与变更相称
- PR 的冲突、检查失败、未经授权移除的阻止合并标签应单列为交付问题，不能混同文风问题
- 仓库要求 CLA 时才检查其状态；只有用户要求直接修复他人分支时，才需要核对维护者编辑权限

## R3 质量检查维度

结合 [写作与表达](writing-standards.md)、[页面结构](page-patterns.md)、[示例与事实依据](examples-and-evidence.md) 与 [双语及无障碍](accessibility-and-localization.md) 检查：

1. 目的和位置：是否解决明确读者任务，是否重复已有页面，是否放在适当目录与导航
2. 内容完整：前提、用法、参数、默认行为、支持范围、结果与限制是否足以完成任务
3. 结构：标题层级、章节次序、分节粒度、模板匹配和不同语言/方式是否清晰
4. 事实与代码：公开接口、厂商 SDK、安装包、示例上下文、版本和返回内容是否吻合
5. 语言：术语、语态、指代、标题、营销表达、冗余和代码标识符的语法使用
6. 链接与资源：链接实际存在且目标相符，图标和图片能加载，路径和重定向正确
7. 呈现与可访问性：表格、提示、标签页、图片说明、键盘阅读路径是否合适
8. 双语：两侧事实、参数、例子、警告和链接是否等价，保留外语样本是否有解释
9. 变更完整：相关正文、参数表、示例、更新日志、导航和已有修正是否一致

先核对需求意图，再核对实现事实，不能因为文字流畅就接受一个与需求无关或不准确的修改。实际验证按 E6 分清写作检查、来源核对和执行验证

## R4 问题分级与证据

| 类别 | 判定原则 | 典型问题 |
| --- | --- | --- |
| 严重问题 | 阻止读者完成主要任务、明显误导或存在实际重大风险 | 虚构/错误版本的 API、无法使用的关键示例、关键链接失效、缺少必需前提 |
| 内容与结构 | 必须补充或重组才能达到页面目标 | 关键参数缺失、章节与页面目的不符、重复内容、请求结构只列名称 |
| 语言与规范 | 可明确对照适用规范的表达问题 | 术语不一致、营销措辞、指代不清、标题和说明不准确 |
| 可选改进 | 不影响任务完成且规范允许取舍 | 非必要措辞、图标比例优化、轻微一致性建议 |

不要把主观偏好升级为严重问题。涉及法律、贡献者协议或项目成熟度的收录条件，应单列“贡献/收录条件”并说明来源；不能直接说该页面技术上不可用

每条发现包含：准确位置、具体原文或缺失内容、适用规则、对读者的影响、可执行的修正建议，以及必要的事实依据。行号来自实际文件或当前 PR diff，不用估算行号

缺失章节等无法定位到单行时，明确标为页面级，或定位到最相关标题并说明缺少什么。问题跨多个位置时分别标出。未核实的 API 或链接记录为待核实，不能报告为已证实错误

## R5 报告与审阅建议

粗看使用短列表或表格，列代表问题并说明范围。完整审查按 R4 四类组织，没有问题的类别明确写“无”；以影响读者成功使用的事项优先

完整 PR 审查可提供：

- 简短总体审阅意见：变更目标、整体判断、主要原因和所需修正
- 建议结论：通过、请求修改、建议关闭，或有明确理由的暂无法判断
- 行级评论草稿：每条发现至少对应一条，跨位置的问题对应多条，不能在摘要中提到后又遗漏评论

给行级意见时定位到实际改动行；缺失内容用明确的页面级说明。报告和评论逐项对齐，措辞简短、直接、礼貌，允许作者补充证据或删除不必要内容。使用目标环境支持的评论形式，不要求复制 Google 的表情分级

| 建议 | 适用条件 |
| --- | --- |
| 通过 | 没有必须修复的问题，至多剩下可选建议 |
| 请求修改 | 内容有价值且可修复，但仍有影响使用、结构或规范的问题 |
| 建议关闭 | 内容重复、已被取代、超出收录范围、核心能力不存在，或有明确无法满足的贡献条件 |
| 暂无法判断 | 关键事实无法核实，且必须补充的信息已明确列出 |

不能仅因为存在一个可修正链接或样式问题就自动建议关闭。未发布功能是否可收录取决于目标 Preview 规则；稳定版文档不得把它写成已发布事实

多个贡献需要整理时，可建议在原分支小修、合并重复内容或创建集中修订，但根据实际差异选择，不把 Google 的“常见做法”当成固定默认动作。所有建议、审阅文字和评论默认是草稿，只有已有明确授权时才发布

## R6 修复与交付

- 用户只要求审查时，报告后完成任务，不擅自改文档、提交评论或改变 PR 状态
- 用户已经授权修复时，直接完成范围内的必要修改，不因 Skill 再索取重复许可
- 尽量保留作者表达，区分自家接口问题与厂商 SDK 问题；未授权不去修改厂商仓库
- 修改后核对事实、渲染及相关链接，必要时验证示例；验证强度与改动风险及用户要求相称
- PR 描述说明读者遇到的问题、改后行为和验证结果，可附预览地址及关联 Issue；不强制使用 Google 特定标题、机器人来源字段或工作流程

## R7 第三方集成的价值与成熟度

仅在用户要求判断能否收录、评估集成贡献，或目标仓库明确要求时开展；普通文案修改不自动触发平台调研

Google 的贡献准入关注完整且可测试、对开发者有用、可公开发布。检查真实接入点以及页面承诺是否有证据，不依赖 PR 自述或营销描述

| 维度 | 可核实的证据 |
| --- | --- |
| 包真实存在 | 发布记录、首次发布时间、发布次数、最新版本、语言版本要求、下载数据 |
| 源码与维护 | 仓库创建时间、提交与贡献记录、发布记录、许可证、近期维护情况、star/fork 等辅助信号 |
| 实际采用 | 包下载、依赖项目、公开生产案例、独立第三方资料和运营时间 |
| 集成真实性 | 使用真实的插件、回调、工具集或协议；是否只是通用 HTTP 包装或修改其他依赖 |
| 网站与链接 | 真实产品网站、有效文档与源码地址，而非占位页或停放域名 |
| 发布边界 | 贡献者授权和目标仓库实际收录条件，是否存在已证实的发布障碍 |

每个判断引用真实来源，数据不可得时说明未知。新项目、同日发布的包、单个贡献者或低下载量都不能单独证明低质量；成熟厂商的新包、有清晰价值和测试的早期项目可以成立

只有多个负面信号与无法验证的功能承诺同时出现时，才形成有依据的疑虑。证据混合时保持中立、给贡献者补充材料的机会，明确这是维护者的收录判断，不当作自动拒绝规则

## R8 反馈措辞模板

按具体事实改写，不直接发送模板，也不使用未核实的理由：

- 完整性：“示例目前缺少服务地址的准备方法，读者无法完成连接。请补充获取步骤，或链接到可直接执行的完整示例”
- 适用范围：“本页的接入方式已由现有页面覆盖。建议在现有页补充这项差异，并将平台专属说明链接到厂商文档”
- 重复内容：“本次变更已由关联页面或已合并修改覆盖，建议复用该说明，避免维护两份相同内容”
- 价值与成熟度：“目前可核实的材料还不足以确认所述集成能力，请补充发布包、源码和使用证据，供维护者判断是否收录”
- 发布条件：“本次贡献尚未满足仓库明确要求的发布条件，请先补充对应授权或材料，再继续审查”

反馈描述问题与解决途径，不评价作者能力；接近拒绝的结论给出事实、适用条件和可以补充的材料
