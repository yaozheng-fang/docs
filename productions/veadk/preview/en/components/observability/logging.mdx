Since 1.0.5, VeADK uses Python's standard `logging` package for runtime logs and no longer depends on Loguru. VeADK loggers live under the `veadk` namespace and write to standard output by default, which works with container platforms and log collectors.

## Set the log level

Set `LOGGING_LEVEL` before importing VeADK. Its default is `DEBUG`.

```bash lines
export LOGGING_LEVEL=INFO
python app.py
```

Use standard Python logging levels, including `DEBUG`, `INFO`, `WARNING`, `ERROR`, and `CRITICAL`.

## Log format

Each record contains the time, level, call location, and message:

```text lines
2026-07-14 10:30:00 | INFO | app.py:20 - Request completed
```

When code runs inside a recording OpenTelemetry span, VeADK adds `trace_id` so you can correlate a request between logs and traces:

```text lines
2026-07-14 10:30:00 | INFO | app.py:20 | trace_id=0123456789abcdef0123456789abcdef - Request completed
```

Interactive terminals use colors for the time, level, and location. Redirected or collected standard output does not contain ANSI color escape sequences.

## Integrate application logs

Your application can use standard-library loggers and control the `veadk` namespace independently:

`LOGGING_LEVEL` controls VeADK logs. Configure your application logger with its own handler, or call `logging.basicConfig()` before importing VeADK. By default, `basicConfig()` does not reconfigure an existing root handler. This example should print `Agent initialized`

```python lines
import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s | %(name)s | %(message)s")

from veadk import Agent
logging.getLogger("veadk").setLevel(logging.INFO)
app_logger = logging.getLogger("company_assistant")

agent = Agent(name="company_assistant")
app_logger.info("Agent initialized")
```

The VeADK handler does not propagate to the Python root logger, which prevents duplicate output when the root logger is configured separately. To send VeADK records to a custom backend, attach a standard `logging` handler to `logging.getLogger("veadk")`.

## Dispatch boundary logs

VeADK emits structured dispatch boundary logs at the INFO level to help locate request latency and call-chain issues. Each log line carries a bracketed prefix identifying the stage, along with fields such as session ID, model name, and elapsed time. Durations are expressed in milliseconds using a monotonic clock.

| Prefix | Source | What is logged |
| :--- | :--- | :--- |
| `[turn-dispatch]` | `Runner` | Start and end of each run turn, plus start and end of trace data saving — includes session ID, message count, output length, and total elapsed time. |
| `[tool-dispatch]` | Tool dispatch layer | Entry and exit of function-tool calls, tool name, thread-pool configuration, parallel-call count; for `run_code` and `bash_tool` — entry, remote-call or subprocess start and end, timeout, and cancellation. |
| `[llm-dispatch]` | Model clients | Preparation, dispatch, first-delta arrival, and completion of model requests — includes model name, streaming mode, input item count, tool count, response count, and total elapsed time; records TTFT when the first output arrives. When a protocol response ID is observed, an additional log line is emitted with the model name, wire protocol, and response ID. |
| `[http-dispatch]` | Volcengine signed requests | HTTP request send start and end — includes action, host, status code, request body size, and elapsed time. |

<Note>
Dispatch boundary logs are emitted at the INFO level. Set `LOGGING_LEVEL` to `INFO` to see them; `DEBUG` is not required. Logging failures do not affect agent execution.
</Note>

## Streaming output logs

During streaming execution, `Runner` does not log each partial chunk. Reasoning is logged once when a complete section finishes, while final answers, tool calls, and tool results are recorded as complete events. Events are still streamed unchanged to the caller; this behavior only reduces token-by-token log noise.

<Warning>
  `DEBUG` records can contain model output, reasoning, tool arguments, and tool results. When production traffic contains sensitive data, set `LOGGING_LEVEL` to `INFO` or higher and apply suitable access and retention controls to collected logs.
</Warning>
